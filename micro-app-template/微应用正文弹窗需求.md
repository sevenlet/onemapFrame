# DialogService 支持微应用正文组件需求

## 1. 文档目的

当前 DialogService 的弹窗外框由一张图平台宿主渲染，正文通过宿主侧动态组件加载。现希望扩展一种正文类型：弹窗外框仍由宿主渲染，但正文可以由微应用提供并在弹窗内容区域内运行。

本文用于评估弹窗组件、DialogService 和 micro-app 宿主是否具备实现条件，并明确建议的调用方式、通信方式、生命周期和验收标准。

## 2. 背景

### 2.1 当前运行结构

```text
一张图平台宿主（基座）
└── micro-app iframe
    └── 大屏微应用
```

微应用通过 RPC 调用宿主的 DialogService：

```js
const dialogId = await callBase('dialogService', 'open', {
  id: 'station-detail-dialog',
  title: '站点详情',
  component: 'stationDetailComponent',
  params: {
    stationCode: '001',
  },
});
```

当前 `component` 是宿主已注册的 LEGO 组件或 Vue 组件名称。宿主在弹窗正文插槽中解析并渲染该组件。

### 2.2 当前限制

微应用自己的 Vue 组件不能直接作为 `component` 传给宿主，原因包括：

1. 微应用运行在独立 iframe/window 和 Vue 应用实例中。
2. Vue 组件对象包含函数、模块引用和运行时状态，不能通过当前 RPC 数据通道可靠序列化。
3. 宿主无法仅凭微应用内部组件名称访问微应用打包模块。
4. 弹窗插槽虽然可以渲染动态内容，但插槽内容必须是宿主运行环境能够创建的 VNode 或组件。

因此，不能直接实现以下调用：

```js
// 不可行：不能跨 iframe 传递 Vue 组件对象。
await callBase('dialogService', 'open', {
  component: StationDetailDialog,
});
```

也不能只传微应用内部组件名并期望宿主自动加载：

```js
// 除非宿主也注册了该组件，否则无法解析。
await callBase('dialogService', 'open', {
  component: 'StationDetailDialog',
});
```

## 3. 需求目标

实现以下结构：

```text
一张图平台宿主
└── 宿主弹窗外框
    └── 弹窗正文插槽
        └── micro-app iframe
            └── 微应用专用正文页面/组件
```

目标能力：

1. 弹窗外框由宿主渲染，可以覆盖整个大屏，不受原大屏微应用 iframe 边界裁切。
2. 正文由指定微应用提供，可以使用该微应用自己的 Vue 组件、依赖和业务逻辑。
3. 调用方不直接传微应用部署 URL，由宿主根据微应用 ID 查询注册表。
4. 支持宿主向正文微应用下发初始化参数。
5. 支持正文微应用主动关闭弹窗并返回业务结果。
6. 支持弹窗关闭时正确卸载正文微应用并清理监听器。
7. 保持现有宿主组件正文模式兼容，不影响现有 `component + params` 调用。

## 4. 非目标

本需求不要求：

1. 将微应用 Vue 组件对象跨 iframe 传给宿主。
2. 由宿主动态 import 微应用内部任意 `.vue` 文件。
3. 引入 Module Federation 或远程模块共享机制。
4. 将微应用组件复制或注册到宿主组件库。
5. 修改普通微应用内部 `el-dialog` 的行为。

## 5. 建议 API

### 5.1 保持现有宿主组件模式

现有调用继续支持：

```js
const dialogId = await callBase('dialogService', 'open', {
  id: 'host-station-detail',
  title: '站点详情',
  component: 'stationDetailComponent',
  params: {
    stationCode: '001',
  },
});
```

语义：

```text
component = 宿主已注册的正文组件名称
params    = 传给宿主正文组件的参数
```

### 5.2 新增微应用正文模式

建议新增 `content` 配置，避免复用 `component` 字段造成语义混乱：

```js
const dialogId = await callBase('dialogService', 'open', {
  id: 'micro-station-detail',
  title: '站点详情',
  initialSize: 'large',
  showMask: true,
  content: {
    type: 'micro-app',
    appId: 'environment-dashboard',
    page: '/dialog/station-detail',
    params: {
      stationCode: '001',
      stationName: '示例站点',
    },
  },
});
```

字段说明：

| 字段 | 必填 | 说明 |
|---|---:|---|
| `content.type` | 是 | 固定为 `micro-app` |
| `content.appId` | 是 | 微应用注册 ID，由宿主通过注册表解析 URL |
| `content.page` | 是 | 微应用内部专用正文路由，例如 `/dialog/station-detail` |
| `content.params` | 否 | 传给正文微应用的可序列化业务参数 |

不建议调用方传入以下字段：

```js
{
  microAppUrl: 'http://localhost:5175/',
}
```

原因：

1. 地址应由平台注册表统一管理。
2. 避免任意 URL 被嵌入宿主弹窗。
3. 部署地址变化时无需修改业务代码。
4. 与现有 `micro-app-registry.json` 管理方式保持一致。

## 6. 可选的等待结果 API

当前 `open` 建议继续保持“打开后立即返回 dialogId”的语义：

```js
const dialogId = await callBase('dialogService', 'open', options);
```

如果业务需要等待用户在正文中完成选择，建议评估新增：

```js
const result = await callBase('dialogService', 'openAndWait', {
  id: 'region-picker-dialog',
  title: '选择区域',
  content: {
    type: 'micro-app',
    appId: 'environment-dashboard',
    page: '/dialog/region-picker',
    params: {
      defaultCode: '350100000000',
    },
  },
});
```

用户确认后，期望返回：

```js
{
  confirmed: true,
  code: '350100000000',
  name: '福州市',
}
```

建议 API 语义：

| 方法 | 返回值 | 说明 |
|---|---|---|
| `open` | `dialogId` | 打开后立即返回，适合后续通过 ID 管理 |
| `openAndWait` | 关闭结果 | 等待正文调用确认或关闭，适合选择器、表单等场景 |
| `close` | `boolean` | 关闭指定弹窗，可选携带业务结果 |

如果现有 DialogService 不适合新增 `openAndWait`，也可以暂时只实现 `open`，结果通过业务事件或全局数据传递。需要弹窗组件侧评估最合适的方式。

## 7. 宿主侧渲染建议

### 7.1 正文类型判断

宿主弹窗正文区域建议保留现有组件分支，并新增微应用分支：

```vue
<template>
  <component
    v-if="dialog.component"
    :is="resolveHostComponent(dialog.component)"
    v-bind="dialog.params"
  />

  <micro-app
    v-else-if="dialog.content?.type === 'micro-app'"
    :name="resolveDialogMicroAppName(dialog)"
    :url="resolveDialogMicroAppUrl(dialog)"
    :data="resolveDialogMicroAppData(dialog)"
    iframe
    @datachange="handleDialogMicroAppData(dialog.id, $event)"
  />
</template>
```

以上代码仅用于表达需求，具体应使用现有弹窗组件和 micro-app 封装方式实现。

### 7.2 微应用实例名称

正文微应用实例名称必须唯一，不能直接复用原大屏微应用实例名称。

建议格式：

```text
dialog-{appId}-{dialogId}
```

例如：

```text
dialog-environment-dashboard-micro-station-detail
```

如果同一弹窗 ID 可以重复打开，应增加实例序号或随机标识。

### 7.3 微应用 URL 解析

宿主根据 `appId` 从微应用注册表获取基础地址：

```text
appId: environment-dashboard
    ↓
micro-app-registry.json
    ↓
url: /micro-apps/environment-dashboard/
```

然后将 `page` 作为微应用内部路由传递。

需要根据微应用当前使用的 hash 路由决定最终 URL 形式，例如：

```text
/micro-apps/environment-dashboard/#/dialog/station-detail
```

不建议简单字符串拼接，应处理：

1. 基础 URL 是否以 `/` 结尾。
2. `page` 是否以 `/` 开头。
3. hash 路由与 query 参数顺序。
4. 部署在子目录时的相对路径。

### 7.4 下发给正文微应用的数据

宿主至少应下发：

```js
{
  dialogContext: {
    dialogId: 'micro-station-detail',
    parentAppId: 'environment-dashboard',
    contentAppId: 'environment-dashboard',
    page: '/dialog/station-detail',
  },
  params: {
    stationCode: '001',
    stationName: '示例站点',
  },
}
```

建议将系统上下文与业务参数分开，避免业务字段与 `dialogId` 等内部字段冲突。

## 8. 正文微应用实现建议

微应用增加专用正文路由：

```js
{
  path: '/dialog/station-detail',
  component: () => import('@/views/dialogs/StationDetailDialog.vue'),
}
```

该路由应只渲染正文内容，不重复渲染完整大屏壳、菜单或首页。

正文组件通过微应用 bridge 获取宿主下发的数据：

```js
import { computed } from 'vue';
import { useBaseBridge, callBase } from '@/bridge.js';

const { baseData } = useBaseBridge();

const dialogId = computed(
  () => baseData.value?.dialogContext?.dialogId,
);

const dialogParams = computed(
  () => baseData.value?.params || {},
);

async function confirm() {
  await callBase(
    'dialogService',
    'close',
    dialogId.value,
    {
      confirmed: true,
      stationCode: dialogParams.value.stationCode,
    },
  );
}
```

具体关闭 API 需要以弹窗组件侧最终确认的协议为准。

## 9. 关闭与结果回传协议

建议支持以下两种关闭来源。

### 9.1 用户关闭宿主弹窗

例如点击右上角关闭按钮、遮罩或宿主底部按钮：

```text
宿主关闭弹窗
    ↓
卸载正文微应用
    ↓
如使用 openAndWait，则 resolve(null) 或标准取消结果
```

建议取消结果统一为：

```js
{
  confirmed: false,
  reason: 'cancel',
}
```

或者统一返回 `null`，但需要平台明确约定。

### 9.2 正文微应用主动关闭

正文微应用调用：

```js
await callBase('dialogService', 'close', dialogId, result);
```

宿主收到后：

1. 校验调用方是否有权关闭该 dialogId。
2. 保存或转发 result。
3. 关闭弹窗。
4. 卸载正文微应用。
5. 如果由 `openAndWait` 打开，则 resolve(result)。

## 10. 更新能力

现有 `dialogService.update(dialogId, partialOptions)` 应评估是否支持更新微应用正文数据：

```js
await callBase('dialogService', 'update', dialogId, {
  title: '更新后的标题',
  content: {
    params: {
      stationCode: '002',
    },
  },
});
```

期望：

1. 仅更新 `params` 时，不重新加载正文微应用。
2. 宿主通过 micro-app data 通道向正文实例下发新参数。
3. 修改 `appId` 或 `page` 时，可以选择禁止更新，或明确执行卸载后重新加载。
4. 需要明确深合并还是整体替换语义。

建议第一版限制为：

```text
允许更新 title、size、locked、showMask 和 content.params；
不允许运行中更新 content.appId 和 content.page。
```

## 11. 生命周期要求

### 11.1 打开

1. 校验弹窗参数。
2. 根据 appId 查询微应用注册信息。
3. 创建唯一微应用实例名称。
4. 创建宿主弹窗。
5. 挂载正文微应用。
6. 下发 dialogContext 和 params。

### 11.2 更新

1. 更新弹窗自身配置。
2. 若 params 变化，通过 data 通道通知正文微应用。
3. 避免因普通参数变化重复创建 iframe。

### 11.3 关闭

1. 标记弹窗进入关闭状态，避免重复 close。
2. 解除 datachange 和全局数据监听。
3. 卸载正文微应用实例。
4. 清理 iframe、定时器和缓存引用。
5. 从 DialogService 实例列表移除弹窗。
6. resolve 等待结果或发送关闭事件。

### 11.4 异常

需处理：

1. appId 不存在。
2. 微应用地址加载失败。
3. 页面路由不存在。
4. 正文微应用初始化超时。
5. 同一 dialogId 重复打开。
6. 正文微应用关闭时弹窗已经不存在。
7. 宿主销毁时仍有正文微应用运行。

## 12. 安全要求

1. 调用方只能传 `appId`，不能直接传任意远程 URL。
2. appId 必须存在于平台微应用注册表或允许列表中。
3. page 应限制为应用内部路径，禁止 `javascript:`、协议 URL 和路径注入。
4. params 应为可序列化普通数据，禁止函数、DOM、Vue 实例等对象。
5. 正文微应用关闭弹窗时，宿主应校验调用方身份和 dialogId 归属。
6. DialogService RPC 继续使用方法白名单，不能向微应用暴露 `destroy`、`configure`、`resetConfig` 等宿主管理方法。

## 13. 兼容性要求

1. 不修改现有宿主组件正文调用协议。
2. 现有 `component + params` 弹窗行为保持不变。
3. 新增的微应用正文能力应为可选分支。
4. 未提供 `content` 时，继续按现有组件方式渲染。
5. 如果同时传入 `component` 和 `content`，应明确报错，避免优先级不清晰。
6. 第一版可只支持 iframe 沙箱模式，后续再评估 default 沙箱。

## 14. 性能要求

1. 微应用正文应支持懒加载，只在弹窗打开时加载。
2. 弹窗关闭后默认销毁正文实例，避免后台逻辑继续运行。
3. 是否缓存正文微应用实例应由弹窗组件侧评估；第一版建议不缓存，以降低状态和资源泄漏风险。
4. 同一页面频繁打开时，需避免重复注册全局监听器。
5. 正文专用路由应轻量，不应初始化完整大屏中的非必要模块。

## 15. 建议的数据结构

```ts
interface DialogOptions {
  id?: string;
  title?: string;
  initialSize?: 'small' | 'large';
  locked?: boolean;
  showMask?: boolean;
  component?: string;
  params?: Record<string, unknown>;
  content?: MicroAppDialogContent;
}

interface MicroAppDialogContent {
  type: 'micro-app';
  appId: string;
  page: string;
  params?: Record<string, unknown>;
}

interface DialogContext {
  dialogId: string;
  parentAppId?: string;
  contentAppId: string;
  page: string;
}
```

如现有 DialogService 使用其他命名规范，可以调整字段名，但建议保留“宿主组件”和“微应用内容”两个明确分支。

## 16. 验收标准

### 16.1 基础打开

- [ ] 微应用可通过 `dialogService.open` 打开宿主弹窗。
- [ ] 宿主弹窗正文成功加载指定 appId 和 page。
- [ ] 弹窗能够覆盖原大屏微应用 iframe 边界。
- [ ] 正文微应用能够使用自己的 Vue 组件和依赖。

### 16.2 参数传递

- [ ] 正文微应用可获取 dialogId。
- [ ] 正文微应用可获取调用方传入的 params。
- [ ] 两个同时打开的弹窗不会串用参数。

### 16.3 更新

- [ ] `update` 修改标题、尺寸等配置后立即生效。
- [ ] `update` 修改 content.params 后正文微应用能收到最新值。
- [ ] 更新参数不会无故重新加载正文微应用。

### 16.4 关闭

- [ ] 宿主关闭按钮可以关闭弹窗并卸载正文微应用。
- [ ] 正文微应用可以主动关闭所属弹窗。
- [ ] 重复关闭不会抛出未处理异常。
- [ ] 关闭后不存在残留 iframe 和数据监听器。

### 16.5 结果回传

- [ ] 如果实现 `openAndWait`，调用方能获取正文确认结果。
- [ ] 用户取消时返回值符合统一约定。
- [ ] 多弹窗并发时结果不会串到其他调用。

### 16.6 异常与安全

- [ ] appId 不存在时返回明确错误。
- [ ] page 非法时拒绝加载。
- [ ] 微应用加载失败时弹窗显示可理解的错误状态。
- [ ] 调用方不能通过参数加载任意外部 URL。
- [ ] 微应用不能关闭不属于自己的弹窗。

### 16.7 向后兼容

- [ ] 现有 `component + params` 弹窗不受影响。
- [ ] 现有 open、update、close、closeAll、setLocked、isOpen、get、getParams 行为保持兼容。

## 17. 最小可行版本建议

第一阶段建议只实现以下能力：

1. `dialogService.open` 支持 `content.type = 'micro-app'`。
2. 宿主根据 appId 获取 URL，并按 page 加载正文微应用。
3. 宿主下发 dialogId 和 params。
4. 正文微应用可调用 `dialogService.close(dialogId, result)`。
5. 关闭时销毁正文微应用。
6. `update` 只支持更新标题、尺寸和 content.params。
7. 暂不实现缓存、跨弹窗复用和复杂嵌套。

第二阶段再评估：

1. `openAndWait`。
2. 加载状态和错误重试。
3. 微应用正文实例缓存。
4. 多层嵌套限制和递归检测。
5. 更完整的权限校验和调用方身份传递。

## 18. 需要弹窗组件侧重点确认的问题

请结合当前弹窗组件和 DialogService 实现，重点评估以下问题：

1. 当前正文插槽是否允许渲染 `<micro-app>` 或一个包含 `<micro-app>` 的宿主包装组件？
2. 当前 DialogService 的正文渲染逻辑在哪里，是否已经支持自定义 slot/render/component？
3. 是否必须修改弹窗基础组件，还是只需要在 DialogService 的正文渲染层增加一个微应用包装组件？
4. 当前弹窗关闭流程是否支持携带 result？
5. 是否适合新增 `openAndWait`，还是应通过现有事件机制返回结果？
6. 当前 `update` 是深合并还是整体替换，如何更新正文微应用 params？
7. 当前弹窗销毁钩子是否可以保证正文 micro-app 实例完整卸载？
8. 同一个微应用地址能否在原大屏和弹窗中同时创建两个 micro-app 实例？需要哪些唯一 name 或沙箱配置？
9. micro-app 是否允许在当前宿主弹窗 DOM 层级中正常运行 iframe 模式？
10. 微应用注册表中已有的 id、url、defaultPage 字段能否直接用于该功能？
11. 当前 RPC 是否携带调用方微应用名称，能否校验 dialogId 归属？
12. 是否存在弹窗正文尺寸计算、缩放或 overflow 规则，会影响 iframe 高度铺满？
13. 是否有 CSP、跨域、Cookie 或鉴权限制会阻止正文微应用在第二个 iframe 中运行？
14. 当前平台是否允许同一微应用重复初始化全局变量、Socket 和路由？是否需要增加“弹窗正文模式”启动参数？

## 19. 期望评估输出

请弹窗组件侧 AI 或开发者给出：

1. 结论：可直接支持、需要小改、需要较大改造或不建议支持。
2. 当前弹窗组件中与正文 slot/component 渲染相关的文件和核心代码位置。
3. 推荐实现方案及其调用 API。
4. 需要修改的文件、模块和大致改动范围。
5. micro-app 实例的创建、更新、关闭和销毁方案。
6. 结果回传方案。
7. 已知风险和不兼容点。
8. 是否建议先实现最小可行版本。
9. 如不建议嵌套 micro-app，请给出可以使用微应用自有正文组件的替代方案。
